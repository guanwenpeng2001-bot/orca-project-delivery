# 项目 Agent 规则

> 本文件是协调者（Coordinator）与所有 Worker 的共同项目规范。  
> 本文件与 `.dev-work/` 都是项目本地状态，默认不进入 Git。  
> Orca 的命令、参数、生命周期和恢复方式，以当前安装的全局 `orchestration` / `orca-cli` Skill 与 `--help` 为准；不要凭记忆拼接命令。

## 1. 适用范围与优先级

本文件约束在本项目中工作的所有 Agent（侦察、需求、方案、裁决、架构、实施、审查、验收）。冲突时按优先级处理：

1. 用户对本次目标的明确要求；
2. 本文件及任务目标目录范围内更具体的 `AGENTS.md`；
3. 当前 Task Contract；
4. 当前 Role Contract；
5. 协调者指定的专业 Skill；
6. Agent 自身默认习惯。

Role、Skill、模型默认值和通用最佳实践不得覆盖项目规则。

## 2. 决策归属

遇到决策先判断归属，再行动。

| 归属 | 条件 | 处理方式 |
| --- | --- | --- |
| Agent 自行决定 | 可逆；局部；不改变用户已定功能方向、业务口径或交付分支；可依据代码、测试、文档或运行证据可靠判断；失败代价有限且可任务内返工 | 直接决定并继续；按推进收益、返工成本、残留物、配额、可逆性综合选择，报告中说明关键判断 |
| 必须交给用户 | 方向性取舍；修改用户既定规则、口径、范围或交付分支；只有用户掌握的信息；不可逆操作；越出本机或影响共享环境、外部系统、生产数据；用户锁定的 Agent、模型或方案无法满足 | 只挂起相关任务，不阻塞其他独立工作；收尾单独汇总，用平实语言说明是什么、不处理会怎样、有哪些选项、建议哪个 |

## 3. 协调者控制工作区

协调者控制工作区是控制面，不是源码开发线。

- 同一控制工作区同一时间只允许一个 Coordinator Agent。
- 控制分支只承载协调者会话、`AGENTS.md`、`.dev-work/` 和业务编排状态：不开发源码、不接收源码任务分支合并、不作为任务基线、审查目标或最终交付来源。
- 协调者控制分支是否跟随源码更新不影响交付；涉及最新源码事实时必须读取实际 `delivery_branch` 或目标任务分支的工作树；不得把控制树的 HEAD、文件或测试结果当成最新集成状态。
- 控制分支必须与 `delivery_branch` 不同，不得在交付分支上启动协调者会话。`scripts/bootstrap-project.ps1` 在当前分支等于解析出的交付分支时拒绝初始化，除非显式传 `-AllowControlEqualsDelivery` 承担控制/交付分离违规的责任（见 `SKILL.md` 的 `Bootstrap` 节）。

## 4. 交付分支

每一轮开发必须确定一个且仅一个 `delivery_branch`：用户明确指定时用指定分支；未指定时用仓库默认分支（解析顺序：`origin/HEAD` → `init.defaultBranch` → `main` → `master` → 当前分支）并记录来源；确定后未经用户明确修改不得自行更换。

`delivery_branch` 是默认任务基线、已验收源码的集成目标、最终集成验证的来源。源码不得通过协调者控制分支中转。

## 5. 任务隔离与分支

所有子代理任务都必须使用独立分支和独立工作树：侦察、技术研究、产品分析、审计、方案、裁决、架构设计、实施、代码审查、安全审查、修复、最终验证。

- 一个 Task 一个工作分支；一个工作分支同一时刻只有一个写者。
- 没有明确基线要求时从 `delivery_branch` 创建；用户、依赖关系或审查对象指定了基线时从指定分支创建。
- 依赖只表达真实先后；能并行且不会争用同一写入范围的任务必须并行；不构造不必要的深依赖链。
- Worker 不得自行合并自己的分支；合并由协调者监督，在实际检出 `delivery_branch` 的工作树中完成。
- 只读任务通常不产生源码提交；报告归档后即可回收其工作树与分支。

## 6. `.dev-work/` 开发过程工作区

`.dev-work/` 只物理存在于协调者控制工作区，是业务流程状态和开发过程资料的唯一项目本地存储位置。

| 主题 | 规则 |
| --- | --- |
| 初始化与复用 | 不存在时由协调者初始化；已存在时读取并复用；可补齐缺少的标准目录；不清空、不覆盖已有报告；旧结构只做可追溯迁移，不删除无法判断归属的内容 |
| 权限边界 | 只有协调者可以修改 manifest、active run、coordinator lock、run state、task/branch map、最终裁决、最终交付报告。Worker 只能读取 Task 明确列出的过程资料、写入 Task 分配给自己的唯一报告路径；不得修改全局状态、不得覆盖其他任务的报告、不得在自己的工作树内创建第二份 `.dev-work/`。Worker 沙箱无法写协调者工作区外的路径时，返回完整报告，由协调者代为落盘 |
| 状态边界 | Orca Runtime 是 Run、Task、Dispatch、Worker、Message、Gate 和生命周期状态的权威来源；Git 是源码、分支和提交的权威来源；`.dev-work/` 保存业务阶段、映射、方案、报告、决策和证据，不得成为第二套 Orca 生命周期数据库 |

## 7. Role 与专业 Skill

每个 Worker 必须有：一个主 Role、一个明确 Task、协调者指定的 required Skills、必要时的 conditional Skills、明确的权限、分支、输入、输出和验收合同。

- 一个 Task 只设一个主 Role；需要多个互相冲突的身份时拆成多个 Task；Worker 不得自行更换主 Role。
- Worker 不得加载或启动完整的 `orca-project-delivery` 协调 Skill，除非 Task 明确授权为嵌套协调者。
- Worker 必须按 Task 指定方式加载专业 Skill；专业 Skill 只提供方法，不得扩大任务范围；任务完成前必须执行相应验证 Skill 或验证步骤。

## 8. 模型、推理档位与降级

所有 Worker 都是 Claude Code（`--agent claude`）。协调者通过 `orca-project-delivery` 的 `routing/model-routing.json` 选择每个角色的档位链、默认档与最低档，不得凭记忆构造启动参数；Orca 的命令与回执形状以当前安装的全局 `orchestration` Skill 与 `--help` 为准。

每次派发必须记录：requested model/effort、effective model/effort、permission mode、Skill 交付方式、fallback 原因、Orca Task/Dispatch、分支、工作树与报告路径。请求值不等于生效值：effective 只以首次 worker-start 回执的 `launch.effective` 为准；无法核对时记为未知，不得宣称已经生效。

- haiku 档位的请求形态：首选完整 id `claude-haiku-4-5` 加 effort；被 Orca 拒绝或回执不符时回退别名 `haiku` 且不指定 effort，并记录。
- 协调者自己的模型不在路由范围内：不选择、不校验；用户主动说明时仅作记录。
- 升降档只在 Claude 内部沿角色的档位链进行：升档先同模型提 effort、到顶再升模型；降档仅在有明确 rate limit、quota、model unavailable 证据时发生，且不得低于角色的最低档；最低档也不可用时挂起该 Task 并记录，不阻塞其他独立 Task。
- 用户锁定 model/effort 时不得自动升降档；锁定选择不可用时挂起相关 Task 并向用户提问。
- 静默、空等待或 `unverifiable` 不等于额度耗尽，不触发降级；降级不得制造第二个并发写者。
- 实施 Worker 中途失效时，必须先确认原 Worker 已停止或完成交接，保存 Git 状态与 handoff，再由新 Worker 顺序接管。

## 9. 命名规则

新增或改动的文件、目录、变量、函数、分支和任务名称必须表意，使用业务或领域词汇。禁止单字母或编号式名称（`A`、`B2`、`task-1`）、版本式名称（`V1`、`FooV3`）、需要依赖注释才能理解用途的模糊名称。非必要不主动重命名无关的存量代码。

## 10. 工程纪律

- 遵循仓库现有类型检查、测试、格式化、构建和 CI 规则；先确认真实问题和最小充分解，再修改。
- 能以小改动完成时，不引入额外抽象、配置、扩展点或插件机制（YAGNI）；已有机制可以满足时，不重复建立第二套。
- 不以“更安全”为名扩大范围，安全措施只针对真实、已识别风险；不顺手重构无关代码。
- 每一处改动都应能追溯到 Task 或必要修复；Bug 修复必须提供能保护目标行为的回归证据。

## 11. 审查与验收

实施者自检不替代独立审查。

- Reviewer 不直接修改被审查源码；finding 必须有证据、位置、影响和严重程度；不把个人风格偏好当成阻断问题。
- 发现问题后由协调者创建修复 Task；修复完成后重新审查。
- 源码 Task 通过独立审查后直接合入 `delivery_branch`；最终集成验证必须基于最新 `delivery_branch` 的独立工作树。
- 无法验证时必须明确标记，不得声称完成。

## 12. 交付纪律

`delivery_branch` 只接收正式项目内容。不得提交或合并：`.dev-work/`；本地 `AGENTS.md`（除非用户明确决定将其纳入项目）；计划、规格、方案、报告；调研、截图、HTML 产物；验证或调试输出；一次性脚本、导出数据、会话笔记；其他与正式项目交付无关的过程产物。合并或提交前必须复核 Git 状态与 diff，确认过程资料未进入变更。

## 13. 真机与共享环境

优先验证已经运行的服务；不擅自启动重复实例；不擅自重启共享主实例；不写共享数据库或生产数据，除非用户明确授权；任何外部副作用都必须遵守“决策归属”规则。

## 14. Worker 生命周期

Worker 必须遵守当前 Orca preamble 和全局 `orchestration` Skill：

- 生命周期 ID、地址和 capability 以 preamble 为唯一权威；只执行当前 Task。
- 在自然检查点查收协调者消息；能自行判断的事项不要提问；真正阻塞时向协调者提问或 escalation。
- 完成时明确报告 succeeded / failed / unverifiable；`worker_done` 只发送一次；发送完成后停止当前任务，不自行开始新工作。
- 不创建下级协调流程，除非 Task 明确授权为嵌套协调者。

## 15. Task 输入组装

协调者派发 Worker 时，输入按以下顺序组装（与 `SKILL.md` 的 "Worker input order" 一致，共 10 段）：

1. Task Objective；
2. Primary Role；
3. Required / Conditional Skills；
4. 输入与依赖；
5. 允许范围与禁止范围；
6. 分支与工作树合同；
7. `.dev-work` 报告合同；
8. 验收与测试合同；
9. Orca Worker Contract；
10. 适用于当前任务的 `AGENTS.md` 内容。

项目规范放在最终输入的最后部分。已有 `AGENTS.md` 不覆盖、不重写；不存在时才由协调者从全局模板生成。

## 16. 无人值守与权限来源

权限的权威来源是 **Claude Code 自身配置 + 用户在本机的 Orca 设置**。Orca 的 `worker-start` 没有权限旗标，本包只能在报告中记录 requested / effective，不能在派发时设定权限。

- 无人值守（自动批准）仅当以下条件同时成立：项目规则允许，且本任务有界、可预期；工作树隔离，且不接触生产数据、共享服务或密钥；命令范围已知，失败可用任务内返工修正。
- 出现以下任一情形必须回到人工批准：不可逆操作、越出本机、写共享环境或生产数据、任务范围不清、用户要求人工确认。
- 用户锁定模型/档位时的换档不属于无人值守的许可范围：必须挂起并向用户提问。
